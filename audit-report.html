A. Executive Summary

What the product is. A local-first Tauri 2 desktop AI coding agent: a Rust host (src-tauri/src, ~900 KB) wrapping a llama.cpp GGUF engine, 21 remote OpenAI/Anthropic-compatible providers, a real ReAct agent loop with 61 tools, subagents, plan/todo tracking, MCP (stdio + HTTP), skills, RAG-style attachments, an LSP bridge, and a React 19 frontend (ui/). It additionally exposes an OpenAI-compatible local HTTP server on 127.0.0.1:8080.

Bottom line. This is a genuinely functional, unusually ambitious agentic prototype, not a demo shell. The agent loop is real (tool calls are dispatched, results appended as role:"tool", generation resumes), the tool surface is broad, and 432 automated tests pass (152 UI + 280 Rust). However it is not production-ready: security is the weak axis, abort correctness is broken for approved tool calls, seven frontend event channels are silently dead, the release/CI pipeline builds the wrong frontend, and local inference could not be re-verified at runtime because no release binary and no matching GGUF were available.

5.7 / 10

Overall readiness · Maturity Level 3 of 5

Top strengths

  1. Real, bounded ReAct orchestration — not a prompt wrapper.
  2. Deep llama.cpp integration: pool, KV-cache reuse, streaming, cancellation.
  3. Central tool-dispatch chokepoint with backend-enforced policy + HITL.
  4. Working security UI: policy, YOLO, grants, audit.
  5. Solid baseline test volume; both frontends build.

Top blockers (P0)

  1. Default-on, unauthenticated loopback API that can execute agent tasks and filesystem tools (api_server.rs:81,149; commands/settings.rs:239).
  2. API keys stored in plaintext in active-remote.json (commands/model.rs:345,358).
  3. Abort is not honored for tool calls executed after approval — CancellationToken::new() is passed instead of the run token (agent/tools.rs:299–315).
  4. Seven UI event subscriptions never fire — backend emits none of them (ui/src/lib/ipc.ts:736–752).

D. Architecture

┌──────────────────────────── Tauri 2 host (Rust) ────────────────────────────┐
│ commands/  (IPC surface: editor, model, settings, agent, workspace, …)      │
│   ├── agent/  orchestrator.rs ─ tools.rs (61) ─ policy.rs ─ mcp.rs          │
│   │            subagents, plan/todo, checkpoints, hooks, skills             │
│   ├── engine.rs      llama.cpp pool, KV cache, sampler chain, streaming     │
│   ├── remote.rs      21 providers, retries, SSE, native tool calls          │
│   ├── api_server.rs  OpenAI-compatible HTTP on 127.0.0.1:8080 (default on)  │
│   ├── lsp.rs, rag/attachments, hub, session store, logging/audit            │
│   └── persistence: app_data_dir JSON (settings, policy, sessions, keys)     │
├──────────────────────────── React 19 frontend (ui/) ────────────────────────┤
│ pages/ (Chat, Security, Settings, Models…) · context/AppContext.tsx         │
│ hooks/useAgentStream.ts · lib/ipc.ts (invoke + event subscriptions)         │
└──────────────────────────────────────────────────────────────────────────────┘
Legacy: root src/ (documented deprecated) still built by root scripts & CI.

Data flow (chat): UI invoke → agent_run_task → orchestrator builds prompt (system + skills + context) → engine or remote provider → streamed deltas → tool call → policy evaluation → HITL if required → run_tool → result appended → next step → agent://run-trace / tool-event events → UI.

Notable design choices

  • One dispatch chokepoint (run_tool) is the right place for policy — and it mostly works.
  • Cancellation tokens thread through engine and tools, but approval re-entry discards the token.
  • Persistence is plain JSON in the app data dir; no database, no migrations, no atomic replace.
  • tauri.conf.json serves ui/ (frontendDist ../ui/dist, dev port 5173), so ui/ is the shipped app; src/ is legacy but still buildable.

L. Final Verdict — 10 Questions

  1. Does it run? Partially verified. Both frontends build, 432 tests pass; no current release binary, so boot was not re-verified. Historical smoke passed.
  2. Is the agent real or simulated? Real. Tool calls are executed and fed back as role:"tool" in a bounded ReAct loop.
  3. Are the tools real? Yes — 61 tools with a single policy chokepoint, though cancellation and path-containment have defects.
  4. Is model integration real? Yes in code: llama.cpp pool/KV cache/streaming plus 21 remote providers. Live inference was not re-run.
  5. Is it secure? No. Unauthenticated default-on API, plaintext keys, policy bypasses, unsafe-eval.
  6. Is it production-ready? No. Security, abort correctness, CI, release, and E2E gaps are disqualifying.
  7. Strongest subsystem? Agent orchestration + llama.cpp engine integration.
  8. Weakest subsystem? Local API server security, followed by RAG semantics and release engineering.
  9. Maturity? Level 3/5 — defined, tested in parts, not measured or release-hardened.
  10. Time to a credible beta? Estimated 3–6 weeks for one or two engineers to close P0/P1 (estimate, not a measurement).

Verdict: A strong local-first agentic coding prototype with a real engine and a broad tool surface — hold distribution until the four P0 security/correctness issues are fixed and CI/release are made trustworthy.

M. Methodology & Limitations

  • Method: repository mapping → subsystem deep reads (agent engine, model infra, ui/, persistence/RAG/ops) → static tracing of feature paths end-to-end → execution of existing checks only → cross-checking docs against code.
  • Read-only: no source edits, installs, upgrades, or destructive commands. No paid API calls. No secrets reproduced.
  • Limitations: (a) no release binary, so no boot/E2E; (b) required 0.5B GGUF absent, so local inference unverified; (c) remote providers not live-called; (d) the API body-parsing defect is static-only, since socket-level testing requires running the app; (e) UI tests cover helpers, not components/IPC.
  • Confidence: high on architecture, tool/policy code paths, build/test results, and documented-vs-actual drift; medium on runtime behavior of the API server and streaming UI; low on unexercised MCP/HF/LSP paths.
